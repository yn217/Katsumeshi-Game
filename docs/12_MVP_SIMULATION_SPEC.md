# 12. MVPシミュレーション・注文・営業処理（実装規範 v0.4）

最終更新: 2026-11-22。本文中の数値はバランス初期値。ゲームの既存仕様 docs/01、03、05、07 を実装単位に落とした補足仕様である。矛盾した場合は本書の規範ルールを優先する。仕様策定段階であり実装済みではない。

## 1. 時間のモデル
- `day`: 1から始まる営業日番号。初期Day1はチュートリアル。
- `openingRemainingSeconds`: 通常日600から開始し0で下限停止。Day1はnull（時間制限なし）。
- `businessElapsedSeconds`: OPEN/COOKの間のみ加算、Day1は注文の生成条件として使わない。
- `queuedWaitRemainingSeconds`: queuedに限り減算。cooking客は待機切れなし。
- `stageElapsedSeconds`: COOKのアクティブ工程でのみ増加。PAUSE/REACTION/タブ非表示では停止。
- ドメイン演算は固定ステップ1/30秒（tick=1/30）。1フレームの経過時間は最大0.1秒、超過時間は破棄し安全のため一時停止させる。タイマーはゲーム内秒数を正規値とする。
- 画像アニメ/SEは演出クロックであり、会計/注文発行のトリガにしない。

## 2. 初日Day1（チュートリアル）の正規的来客生成
- 固定8件を **regular, student, worker, tourist, regular, student, worker, tourist** の順に生成。タイプは最初から4種類登場。
- 最初の注文はチュートリアルの「開店」操作後に1件queuedとして生成。
- 1件がserved/cancelledになり、そのREACTIONがあれば表示終了した直後、次の注文を1件生成する。queued上限3と矛盾しないよう、**同時に待機中のチュートリアル注文は最大1件**とする。
- Day1の待機時間・営業時間は無制限。空の操作画面で放置しても注文は消えない。
- 8件すべてservedまたはcancelledになったらRESULTへ。ゲームの原価/売上例は**8件すべてserved、材料の追加購入0、アップグレード購入0**の基準ケースに限る。
- 初日仕入0円は基準ケースの条件であり、調理開始後に8食分を超えて消費する機能がないため初期在庫10食分で足りる。

## 3. 通常日の候補来客（Day2以降）
- 一日候補客数 `n = clamp(10 + floor(startOfDayReputation/25), 10, 14)`。評判30で11人、100で14人。結果は0より大きい整数。
- 候補来客の登場時刻 `arrivalSecond[i] = 20 + floor(i*540/n)`、i=0..n-1。540秒の中に候補を分散し、最終候補は開店後600秒未満。
- 客タイプは seed 付きPRNGから重み `regular:30 / student:25 / worker:25 / tourist:20` の重み付き抽選で決定。Day1にはPRNGを使わない。
- 新しい営業日の乱数初期状態は `x=(save.seed ^ Math.imul(day,0x9e3779b9))>>>0`、0なら `0x6d2b79f5` を使う。32bit `xorshift32`: `x^=x<<13; x^=x>>>17; x^=x<<5; x>>>=0;`。一様乱数 `u=x/4294967296` とする。客タイプを重み累積区間 (0..0.30 regular, ..0.55 student, ..0.80 worker, ..1.00 tourist) で選ぶ。
- **候補来客が満員で不採用でも乱数は1回消費する**。各候補でまず客タイプ抽選→キュー空き確認→発行/スキップ。候補時刻を処理するたびに `nextArrivalIndex` を1進め、営業中は `remainingArrivals=n-nextArrivalIndex` を維持する。閉店時は未到着候補を残存0にするが、逸失人数/評判減少には加算しない。再開時に再抽選しない。画像演出用乱数と分離する。
- 候補時刻で **queued<3** の場合だけ注文を発行しqueuedへ。満杯ならその候補は「待機列に入れなかった見込み客」として集計し、注文IDは発行しない。満杯による逸失は当面評判減点しない。
- active cooking注文は最大1件であり、queued3件とは別枠。複数同時調理はMVP外。
- 営業時計600秒で新規来店は止まり、すでにqueued/cookingの注文は最後まで処理する。

## 4. queuedの忍耐と注文受付
- 基本忍耐180秒×客倍率。椅子購入時は更に×1.1。内部では小数秒を保持。表示は `ceil(remaining)`。
- 注文受付ボタンは **OPENかつactiveOrderId=null** かつqueued、在庫が揃い、他のモーダルがない場合のみ有効。
- 受付優先はプレイヤー選択。何も選ばなければ一番古い注文を案内ハイライトする。順番を飛ばしてもペナルティなし。
- 受付成功時に5種の材料各1「食分相当」を引き落とす。1つでも不足なら**原子的に無変更**。受けられない理由と不足数を表示する。
- queued残時間0でexpired。expiredは売上/原価0、評判-2、客は去る。
- 客が期限切れに到達したtickと受付入力が同時刻なら、tickの期限切れ処理を先に実行する（状態を見て受付拒否）。
- cookingへ移った時点で忍耐判定停止。提供前に他客が期限切れになってもactiveOrderはキャンセルされない。

## 5. tick処理の順序
(1) overlay、phase、visibilityをチェック → (2) ゲーム時計更新 → (3) queued忍耐更新とexpired確定 → (4) 通常日の新規来客処理 → (5) ユーザーコマンドを受信順に検証/適用 → (6) 終了可能性判定 → (7) 描画用スナップショット通知。ユーザー操作はtick境界にキューイングし、期限切れ等を処理した後に適用する。actionIdを持たない重複入力はUIでデバウンスし、ドメインではorderIdと操作内容で冪等判定する。

## 6. 閉店
- Day1: 8件すべてが終端（served/cancelled）のとき。
- Day2以降: openingRemainingSeconds=0かつ queued=0、cooking=0、REACTIONでないとき。
- CLOSE_DAYは日付を鍵として一度だけ固定費2,200円（MVP人件費0円）を記録し、RESULTへ。未発送の将来候補はこの時点で破棄。
- 当日のRESULTは保存してからUPGRADEへ。UPGRADEでのみ設備購入可、翌日へ進む際に次のDayを作る。
- ゲーム時計が0でqueuedが在庫不足により受付できなくても、待機期限は減り続けるのでいつかexpiredになり閉店できる。

## 7. タブ非アクティブ・ポーズ
- ページが非表示になったらプレイ時間を止め、再表示時には「一時停止中」を表示。再開ボタンまで進行しない。
- Escapeはoverlayの表示/非表示、二重に同じPAUSEを積まない。
- 保存はGAME STATEの確定入力のみ。ポインターでドラッグ中の位置はキャンセルし、最後の確定値から復元。調理のタイムゲージは復元後停止状態から再開。
- 手動ゲーム終了は**保存成功後にタイトルへ**。保存失敗時は画面を維持し再試行。

## 8. 例外と守るべき不変条件
- 総注文数（生成済み）=queued+cooking+served+cancelled+expired の個数。
- queued<=3、cooking<=1。activeOrderIdはcooking中の注文のIDに等しい。
- served注文は売上と評判が適用済み、expiredは在庫消費なし、cancelledは消費した材料のみロスへ移動。
- 候補来客数と実際のqueued生成数は異なってよい（満員のときの逸失があるため）。
- すべての外部入力はvalidate→state transition→save notificationの順番で処理、二重会計禁止。

## 9. 受け入れ例
- Day1を全8件提供: 売上7,840円、消費原価3,440円、固定費2,200円、営業利益2,200円、現金35,640円、材料在庫各2。
- 通常日評判30: 候補11件、queued上限3。30秒時点では1件目が登場済み。
- queuedが180秒到達時に時間切れ: 1件expired、評判-2、材料原価0。
- openingRemainingSecondsが0でqueued3・cooking1: 来店だけ停止。受付可能なのはactive注文が終端に達してから。
- CLOSE_DAYを2回呼んでも固定費の合計は2,200円のまま。
