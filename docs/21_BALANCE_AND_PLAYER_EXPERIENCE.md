# 21. バランス・進行・ゲーム体験検証（v0.5）

設計の目的は「6工程を8〜14皿繰り返す苦痛」や「材料不足で詰まる」を避け、短時間で気持ちよく料理/経営を繰り返すこと。数値は初期目標でありプレイテスト未実施。

## 成長ループ
1. MORNING: 在庫が需要に合うか判断、たれ2枠を試す。客タイプの好みに合わせるため、選択したソースの違いがランクに反映される。
2. OPEN: 忍耐の減る順に受注するか好みのわかる客を優先するか選択。どれが最善かを固定しない。
3. COOK: タイミング精度と段階的な操作で料理の品質を上げる。出前/ランダムレシピなどはMVP外。
4. REACTION: 完成したかつめしと顧客が主役。調理品質、客の好み、ランクの違いを短い演出で理解する。
5. RESULT: 売上、経費、売れなかった見込み客、評判変化、改善ポイントを示す。
6. UPGRADE: フライヤー/椅子購入→翌日の体験改善。Day7で節目会話、Day8以降エンドレス。

## 初期バランス目標（初期設計値）
| 項目 | 目標 | 必ず測定すること |
| --- | --- | --- |
| 1皿の操作時間 | 初回40〜70秒、慣れて25〜45秒 | 工程別所要時間、入力回数 |
| Day1 | 8皿のチュートリアル（無制限時計） | 完走までの実時間、脱落地点 |
| Day2以降 | 候補10〜14件、営業時間600秒 | 実来客数、提供数、期限切れ数、逸失候補 |
| 初回遊びやすさ | 5人中4人が説明なしでP1/P2/P6を操作可能 | 再試行回数とUI迷い |
| 評価演出 | 1回2〜4秒＋任意スキップ | 6ランクの印象が識別可能か |
| 収支 | Day1の基準例で2,200円利益 | 消費原価・現金と利益の差を理解できるか |
| 進行 | Day1後の設備購入を体験できる | Day2フライヤー購入条件の理解 |
| セーブ | P3途中を含む全phaseから続き再開 | 途中操作/抽選/会計の再現性 |

## 評価分布の注意
- 現行式はP4固定20点と嗜好一致時最大+15点で、**基礎品質80でもSSSに到達**できる。
- 全操作得点が0の場合の下限は5点。見た目の0〜100ゲージと実到達範囲が異なる。MVPではスコア範囲の表現を正直にする。
- 暫定の品質配点そのものを今回のレビューで恣意的に変更しない。プレイテストで高ランクが多すぎるなら `q` や `b` の調整を検討し、ランク分布、客の好み学習、満足度の比較を伴うIssueで審議する。
- 画面表示は「工程品質」「たれと客の相性」「総合点」に分け、固定20点を「たれ操作の上手さ」と誤表示しない。

## 発売前のバランスシミュレーション
- seedを最低100個、プレイヤー技能をpoor/average/goodの3パターン（入力正規化誤差0.8/0.4/0.1、タイミング差4/2/0.5秒等）として7営業日分シミュレーションする。
- 指標: 来店候補数、queued満員逸失、期限切れ、売上、利益、現金、購入設備、評判、平均ランク、SSS割合、支援使用回数。
- 設定JSONを変えた場合は同じseedと技能データで比較し、中央値と極端値を記録する。
- 金銭/評判/在庫が壊れない「安全性」は自動テストで証明し、プレイの面白さは実プレイヤーで評価する。

## 経営バランス上の制限
- 仕入れはMORNINGでのみ可能、各食材上限99。実注文1皿に必要な5種類すべてがなければ調理受付不可。
- 品切れで開店してもqueued客が退出し、Day1の8件のみ初期在庫10で不足しない。Day2以降は支援の条件をMORNINGで説明。
- 無償支援は必要材料を4食分まで補填、既に4食分以上ある品目を加算しない。1日1回。
- 売価980円固定。設備購入はUPGRADEで、翌日の開始時点で効果を適用。

## 進行/難易度
- Day1初回提供/試食を見せて操作学習、その後7件を順次。
- Day2フライヤー効果、Day3椅子効果により操作と待機に一度ずつ明確な改善が生まれる。
- Day7のRESULT確定後に一度だけ節目会話を再生。評判値30/60/80で会話差分（暫定）。条件に失敗しても続行可。
- Day8以降は同じ営業ループ。経験済み操作は早送り演出のみ可能（調理操作そのものの自動化はMVP外）。

## プレイテストでの意思決定
- Day1 8件のチュートリアルが10分超で疲労感を与える場合、工程説明を最初の1皿だけにして残りは短く案内する。それでも長いなら初日件数を変更する仕様変更Issueとする。
- P2のクリック代替30回が負担なら、ドラッグ補助/長押し/セルまとめ塗りを評価する（キー入力側は22の代替操作で操作可能性を確保）。
- 待ち切れ率や満員逸失が高い場合、到着スケジュール・調理目標・忍耐をまとめてチューニングする。根拠なく一つのパラメータのみ変更しない。
- すべてのパラメータ変更に理由、before/after試験値、関連Issueを残す。
